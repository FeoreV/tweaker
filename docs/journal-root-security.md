# Journal root security gate

Status: **partially implemented; system mutation entrypoints must remain disabled.** The current implementation creates and validates a protected local journal root and checks its ancestor DACLs. The remaining namespace-race, cross-account, power-loss, and Windows 7 VM evidence listed below is still required before this becomes a release gate closure.

## Current behavior

`FileJournalStorage::create_private` accepts only a new leaf below an existing path on a fixed NTFS volume that advertises persistent ACL support. `FileJournalStorage::open` applies the same volume requirement. The volume check uses `GetVolumePathNameW`, `GetDriveTypeW`, and `GetVolumeInformationW`, available before Windows 7; see Microsoft's [GetVolumePathNameW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumepathnamew), [GetDriveTypeW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getdrivetypew), and [GetVolumeInformationW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumeinformationw) references. The root path is then checked component-by-component for reparse points and ancestor owner/DACL policy, the leaf is created with a protected DACL, the descriptor is read back, and RAII directory handles are retained for the storage object's lifetime. Existing leaves are rejected rather than repaired. UNC paths and paths containing parent components are rejected.

The root DACL grants SYSTEM full access and gives OWNER RIGHTS a narrow set of journal-directory permissions. A separate inherit-only OWNER RIGHTS ACE grants journal-file read/write/delete permissions needed for marker publication and recovery. OWNER RIGHTS is used so the directory owner does not receive implicit `READ_CONTROL`/`WRITE_DAC`; the explicit ACEs do not grant `WRITE_DAC`, `WRITE_OWNER`, or `DELETE` on the root itself. Existing ACLs are never silently changed.

Windows host tests exercise root creation/open, rejection of an existing or unprotected root, record creation, flush/readback, marker rename, lock reopening and recovery. Both an impersonated anonymous token and a restricted token whose restricting SID is `BUILTIN\Guests` fail to rename the root while storage is open. A process running as the trusted profile owner can rename it through the profile parent's `FILE_DELETE_CHILD`, even while the handles remain open. Same-account hostile processes are outside this ACL boundary because they can also modify journal files with the app's principal. These tests do not prove access behavior under a separate named account or Windows 7.

## Why checking one DACL is insufficient

Windows permits a security descriptor to be supplied when creating a directory. If no descriptor is supplied, the new directory inherits ACL entries from its parent. Even an explicitly supplied DACL can receive inheritable parent ACEs unless it is protected with `SE_DACL_PROTECTED`. See Microsoft's [CreateDirectory contract](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createdirectory), [DACL construction rules](https://learn.microsoft.com/en-us/windows/win32/secauthz/dacl-for-a-new-object), and [security descriptors for new objects](https://learn.microsoft.com/en-us/windows/win32/secauthz/security-descriptors-for-new-objects).

Verifying a leaf DACL once also does not pin the path. The current implementation performs later I/O by path, so a process with rights on the parent may be able to replace or rename the root after verification. A local experiment confirmed that retaining a directory handle opened without `FILE_SHARE_DELETE` does **not** by itself stop `MoveFileEx`/`std::fs::rename` from renaming the directory: Windows also permits rename/delete through `FILE_DELETE_CHILD` on the parent. Microsoft's [DeleteFile contract](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-deletefile) documents the alternative authorization path. Do not count a retained leaf handle as a path pin unless parent `FILE_DELETE_CHILD` is controlled too.

## Required implementation contract

1. Provide a creation path for a **new, absent** journal directory. Do not silently rewrite ACLs on an existing directory; reject it unless a separately reviewed adoption procedure is designed.
2. Create the leaf with an explicit, protected DACL, then read back and validate the resulting owner, DACL and protected-DACL control bit. Fail closed on unsupported filesystems or API errors.
3. Resolve and validate the parent path and its security before creation. Ensure untrusted principals cannot replace/delete the leaf through either leaf `DELETE` or parent `FILE_DELETE_CHILD`, nor redirect path resolution. Reject reparse points in every relevant component, not only the leaf.
4. Prevent path substitution for the lifetime of `FileJournalStorage`. The implementation retains no-delete-sharing handles and rejects untrusted delete/ACL-owner rights on ancestors, but all journal I/O still uses path-based APIs. Host tests deny replacement by anonymous and restricted Guests tokens and confirm that a trusted profile owner can still rename through the parent's `FILE_DELETE_CHILD`. Bound the protection claim to untrusted principals; privileged actors and hostile processes under the same user remain outside it. A leaf handle without delete sharing is not enough.
5. Preserve Windows 7 SP1 x86/x64 compatibility. Use only APIs present on Windows 7; wrap every returned handle or LocalAlloc buffer in an RAII owner; keep ACL conversion, creation, readback and error cleanup in one audited module.
6. Tests must use disposable directories and verify: the created ACL and protected bit, rejection of existing roots, rejection of reparse paths, failure cleanup, access from a second unprivileged account where available, and path-replacement attempts while the storage object remains alive. The current host's pre-existing `Application Data` profile junction is used read-only and the reparse-path rejection test passes. A disposable parent with an unsafe `BU` DACL is rejected before creating the journal leaf. A test-only invalid post-create DACL exercises cleanup and confirms the leaf is removed. Anonymous and restricted Guests tokens are denied a live rename while storage is open; the trusted profile owner can rename the root through parent `FILE_DELETE_CHILD`, confirming handles alone do not pin it for a principal already trusted by the parent. Creating a new symlink was unavailable (Windows error 1314), so no new link was created. Separate named-account access remains outstanding. Do not mutate the user's existing ACLs in tests.

## Gate decision

Do not treat a one-time `GetNamedSecurityInfoW` check as sufficient. It can establish what descriptor was read, but not that the path remains bound to that object or that an ancestor cannot replace it. Do not add a broad-principal denylist and call it secure: custom local/domain groups and inherited rights make that incomplete. Until creation, ancestry, lifetime binding and tests satisfy this contract, the existing caller-managed ACL statement remains a release blocker.
