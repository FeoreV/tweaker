# Journal root security gate

Status: **partially implemented; system mutation entrypoints must remain disabled.** The current implementation creates and validates a protected local journal root and checks its ancestor DACLs. The remaining namespace-race, cross-account, power-loss, and Windows 7 VM evidence listed below is still required before this becomes a release gate closure.

## Current behavior

`FileJournalStorage::create_private` accepts only a new leaf below an existing path on a fixed NTFS volume that advertises persistent ACL support. `FileJournalStorage::open` applies the same volume requirement. NTFS and persistent-ACL properties are queried from the retained root handle with `GetVolumeInformationByHandleW`; drive type is checked using the final path obtained from that handle and `GetDriveTypeW`. The root path is resolved component-by-component, opening each child relative to its already validated parent handle and rejecting reparse points. The leaf is created relative to its validated parent with a protected DACL, the descriptor is read back, and RAII directory handles are retained for the storage object's lifetime. Existing leaves are rejected rather than repaired. UNC paths and paths containing parent components are rejected.

The root DACL grants SYSTEM full access and gives OWNER RIGHTS a narrow set of journal-directory permissions. A separate inherit-only OWNER RIGHTS ACE grants journal-file read/write/delete permissions needed for marker publication and recovery. OWNER RIGHTS is used so the directory owner does not receive implicit `READ_CONTROL`/`WRITE_DAC`; the explicit ACEs do not grant `WRITE_DAC`, `WRITE_OWNER`, or `DELETE` on the root itself. Existing ACLs are never silently changed.

Windows host tests exercise root creation/open, rejection of an existing or unprotected root, record creation, flush/readback, marker rename, lock reopening and recovery. Path-based rename and `create_new` attempts under impersonated anonymous and restricted `BUILTIN\Guests` tokens return permission denied. These test roots are below the current user profile, so ancestor traversal or ACLs may also account for the denial; the result does not isolate the journal root DACL. The anonymous test now fails if impersonation cannot be established rather than silently passing. A process running as the trusted profile owner can rename it through the profile parent's `FILE_DELETE_CHILD`, even while the handles remain open. Same-account hostile processes are outside this ACL boundary because they can also modify journal files with the app's principal. These token tests do not prove access behavior under a separate named account or Windows 7.

## Why checking one DACL is insufficient

Windows permits a security descriptor to be supplied when creating a directory. If no descriptor is supplied, the new directory inherits ACL entries from its parent. Even an explicitly supplied DACL can receive inheritable parent ACEs unless it is protected with `SE_DACL_PROTECTED`. See Microsoft's [CreateDirectory contract](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createdirectory), [DACL construction rules](https://learn.microsoft.com/en-us/windows/win32/secauthz/dacl-for-a-new-object), and [security descriptors for new objects](https://learn.microsoft.com/en-us/windows/win32/secauthz/security-descriptors-for-new-objects).

Verifying a leaf DACL once does not pin the path for the storage object's lifetime. A process with rights on the parent can rename the root after it has been opened. A local experiment confirmed that retaining a directory handle opened without `FILE_SHARE_DELETE` does **not** by itself stop `MoveFileEx`/`std::fs::rename` from renaming the directory: Windows also permits rename/delete through `FILE_DELETE_CHILD` on the parent. Microsoft's [DeleteFile contract](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-deletefile) documents the alternative authorization path. Journal operations now remain anchored to retained handles during such a rename, but this does not prevent a same-user actor from editing the moved journal or make the renamed root discoverable after restart.

## Required implementation contract

1. Provide a creation path for a **new, absent** journal directory. Do not silently rewrite ACLs on an existing directory; reject it unless a separately reviewed adoption procedure is designed.
2. Create the leaf with an explicit, protected DACL, then read back and validate the resulting owner, DACL and protected-DACL control bit. Fail closed on unsupported filesystems or API errors.
3. Resolve and validate the parent path and its security before creation. Ensure untrusted principals cannot replace/delete the leaf through either leaf `DELETE` or parent `FILE_DELETE_CHILD`, nor redirect path resolution. Reject reparse points in every relevant component, not only the leaf.
4. Keep journal I/O bound to the validated directory objects. Production child-file open/create, lock files, directory enumeration, readback and cleanup use the retained root/parent handles; marker publication uses `NtSetInformationFile` with native `FILE_RENAME_INFORMATION.RootDirectory`. `NtCreateFile` validates every single-component name and opens with `FILE_OPEN_REPARSE_POINT`; returned handles are checked for object type and reparse attributes. A root-replacement test opens storage, renames the root, creates a valid replacement at the original name, writes a committed record through the old storage, and verifies the files appear only in the moved original. An active transaction test confirms its exclusive lock prevents root rename on this host. These tests establish handle-relative behavior for those cases, not protection from same-user writes or restart rediscovery after a rename. Ancestor replacement, a separate named account, privileged actors and power-loss behavior remain separate gates.
5. Preserve Windows 7 SP1 x86/x64 compatibility. Use only APIs present on Windows 7; wrap every returned handle or LocalAlloc buffer in an RAII owner; keep ACL conversion, creation, readback and error cleanup in one audited module.
6. Tests must use disposable directories and verify: the created ACL and protected bit, rejection of existing roots, rejection of reparse paths, failure cleanup, access from a second unprivileged account where available, and path-replacement attempts while the storage object remains alive. The current host's pre-existing `Application Data` profile junction is used read-only and is rejected; depending on the reparse handle ACL, opening it may fail with `PermissionDenied` before metadata inspection or with `InvalidInput` after inspection. A disposable parent with an unsafe `BU` DACL is rejected before creating the journal leaf. A test-only invalid post-create DACL exercises cleanup and confirms the leaf is removed. Anonymous and restricted Guests token tests and a controlled-parent file-create positive control are recorded above; a trusted profile owner can still rename the root through parent `FILE_DELETE_CHILD` when no exclusive transaction lock blocks it. Creating a new symlink was unavailable (Windows error 1314), so no new link was created. Separate named-account access remains outstanding. Do not mutate the user's existing ACLs in tests.

## Gate decision

Do not treat a one-time `GetNamedSecurityInfoW` check as sufficient. It can establish what descriptor was read, but not that the path remains bound to that object or that an ancestor cannot replace it. Do not add a broad-principal denylist and call it secure: custom local/domain groups and inherited rights make that incomplete. Until creation, ancestry, lifetime binding and tests satisfy this contract, the existing caller-managed ACL statement remains a release blocker.

## Controlled-parent ACL test — 2026-10-28

A new Windows host test, `restricted_users_can_create_parent_file_but_not_journal_file`, uses a disposable parent whose DACL permits BUILTIN\Users the minimal traversal/add-file rights accepted by the journal-root policy. A restricted token with BUILTIN\Users as its restricting SID successfully creates and writes a control file in that parent; the same operation against the protected journal root returns `PermissionDenied` and leaves no file behind. The test removes its control file and the disposable directory. This isolates the file-creation denial from the old test's profile-ancestor ambiguity.

This does **not** test directory rename, `FILE_DELETE_CHILD`, path substitution, root identity binding, second-account behavior, or power loss. The existing trusted profile-owner rename test still demonstrates that the open root can be replaced through the parent. Mutation entrypoints remain disabled.

Verification after the test: focused test passed; `cargo test --locked --all-features` passed (314 library + 23 CLI); all-features check, strict all-target/all-features Clippy, and fmt check passed. Six warnings from vendored Sciter remain.

## Handle-relative storage implementation — 2026-10-28

The production conversion is in place: root ancestry opens one component at a time, and child opens/creates, locks, enumeration, readback, cleanup, and marker publication are rooted in retained handles. Re-checking applies to each returned child handle; root volume properties come from the actual retained handle. A new leaf is created relative to the validated parent with create-exclusive semantics; failed post-create validation marks that exact handle for deletion. Production journal I/O no longer uses metadata-by-path followed by open-by-path.

The reviewed `windows-sys 0.59.0` WDK bindings expose user-mode `NtCreateFile` with `OBJECT_ATTRIBUTES.RootDirectory`, `NtQueryDirectoryFile`, and `NtSetInformationFile`. `NtCreateFile` documentation describes `RootDirectory` as the base handle for a relative name and `FILE_OPEN_REPARSE_POINT` as bypassing reparse processing for the opened component ([Microsoft NtCreateFile](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile)). Although `FILE_RENAME_INFO.RootDirectory` documents relative rename support, `SetFileInformationByHandle` returned `ERROR_INVALID_PARAMETER` on the host for this usage. Marker publication therefore uses native `NtSetInformationFile` with the `FileRenameInformation` class and the matching native-layout structure; this path passes the replacement-root regression test. Volume/ACL capability checks use the actual retained root handle ([Microsoft GetVolumeInformationByHandleW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumeinformationbyhandlew)).

The root replacement regression passed: the original opened storage wrote into the moved original after a valid protected replacement was created at the old path, and the replacement remained empty. An active transaction test also passed and observed that the exclusive lock prevented root rename. An ancestor replacement regression now attempts the same with a nested journal root. On this host Windows denied renaming the open ancestor with `PermissionDenied`; the test then confirms journal I/O still works on the original path. It will exercise the replacement branch on hosts that permit that rename. Separate-account ACL behavior and Win7 VM execution remain unproven. Same-user actors can still modify journal objects through the same principal; a renamed root may not be rediscovered after restart. Marker publication no longer uses the Win32 wrapper because that wrapper failed on this host; power-loss durability and directory-entry persistence remain unproven.

Verification on 2026-10-28: stable MSVC Rust 1.97.1 all-features tests passed (323 library + 23 CLI), locked all-features `cargo check`, strict all-target/all-features Clippy, and `cargo fmt --check` passed. Nightly 1.101.0 release builds with `experimental-ui` passed for `i686-win7-windows-msvc` and `x86_64-win7-windows-msvc`. `dumpbin` and `llvm-objdump` are unavailable in the current shell, so the import audit was not run. No Win7 VM or live system mutation was performed. Six warnings remain in vendored Sciter code.

## Controlled-parent verification update

The restricted Users positive control successfully creates and writes a file in a disposable parent accepted by journal policy; the matching file creation inside the private journal root returns `PermissionDenied` and leaves no file. This isolates one child-file add check from ancestor/profile ACL effects. Attempts to extend the same test to rename the control file were denied by the host ACL/token path, so the test intentionally does not claim to isolate rename or `FILE_DELETE_CHILD`. The trusted profile-owner rename test remains a demonstrated path-replacement limitation. No production write path was enabled.
