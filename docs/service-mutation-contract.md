# Service mutation contract and implementation gate

Status: B2 Win32 SCM prototype implemented behind typed file sessions; service mutation is not approved for the application. `src/engine/services.rs` can change only an existing local service's startup type through `FileTypedTransactionSession::apply_windows` and recover it through `FileTypedRecoverySession::run_windows`. Neither method is wired to UI or CLI. The session commits the typed snapshot before calling the backend, but unresolved shared journal-root gates mean this prototype is not release-ready.

## Initial supported operation candidate

Start with a single-field operation: change the startup type of an existing local Windows service. Do not add service creation/deletion, service start/stop/pause, account/password changes, binary path changes, dependencies, failure actions, or remote SCM operations in this stage. These operations have different side effects and snapshot requirements.

The operation identity is the exact internal service name plus local-machine scope. Query failures (including access denied) are errors, never interpreted as absence. A missing service is rejected. The current backend queries the exact numeric startup type, persists a typed service transaction record containing identity, before value, intended value and transaction/sequence IDs, flushes and validates its committed marker, and only then calls `ChangeServiceConfigW` with unrelated scalar fields set to `SERVICE_NO_CHANGE` and unrelated pointer parameters set to `NULL`, as required by the API contract. It re-queries and checks the intended startup type after the call. It does not start or stop services. This describes code inspection and compile evidence; the setter has not been executed on a service.

Recovery is conflict-aware: if current startup type already equals `before`, report already restored; if it equals `intended`, persist the current pre-restore state to the recovery journal, restore `before`, then re-query and verify; if it equals neither, report conflict and do not overwrite the external change. A service that disappeared, became inaccessible, or cannot be queried is a recovery error, not a successful restore.

## Persistence dependency

Do not encode a service operation as a fabricated registry target. The data layer has a versioned tagged registry/service record codec, strict envelope validation, ordered file scanning, service-only and mixed-resource append/resume writers, and typed checkpoints. Checkpoint format v4 binds ordered typed records while continuing to read v3 registry-only checkpoints. A managed `FileTypedRecoverySession` retains the source transaction lock, checkpoint, separate typed snapshot journal lock and shared mutation barrier. Its typed recovery runner dispatches through the supplied resource backend, commits the pre-restore snapshot before restore, advances checkpoint progress, and rotates to a fresh snapshot journal after an incomplete tail. NTFS-backed tests with the mock SCM exercise apply and recovery through these managed sessions. The service backend is mockable; actual Win32 access-denied mapping and SCM behavior are not yet exercised. Preserve transaction/sequence binding, commit-marker validation, incomplete-tail behavior, and fail-closed compatibility.

The generic typed transaction coordinator establishes this ordering for all backends: exclusive shared mutation barrier, query, durable committed snapshot, then apply. `ScmBackend` re-queries after the durable snapshot and immediately before both apply and restore, rejecting a changed state or target as a conflict. Mock tests cover a change injected during snapshot persistence. This narrows, but cannot eliminate, the external actor race between the final query and `ChangeServiceConfigW`; the app's file barrier is not an SCM-wide lock. `LockServiceDatabase` cannot close this race: Microsoft documents that it has no effect as of Windows Vista, and even on older systems its lock only blocks service starts, not other SCM functions ([LockServiceDatabase](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-lockservicedatabase), [SCM protocol lock behavior](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-scmr/ff71f732-e91d-4189-8fb9-a410674c63ad)). No supported Windows target provides a documented SCM lock for serializing `ChangeServiceConfigW`. The Win32 SCM setter is only called from managed typed sessions; no UI or CLI exposes it. Recovery is conflict-aware and retains retryable journals on partial failure.

## Mock test matrix

Before approving Win32 writes, the mockable SCM adapter now covers exact startup-type application and verification, query failure, snapshot failure, partial change failure, restore retry, wrong-state verification, external conflict before apply/restore, and recovery snapshot failure. NTFS-backed typed apply and recovery sessions verify commit markers before writes, retain the recovery snapshot after failed restore, and resume after reopen. A 21-point fault-injection matrix crosses the mock SCM with each recovery snapshot/checkpoint create, write, flush, readback and publication boundary; it verifies that restore never occurs before its snapshot, retries do not apply restore twice, and another reopen accepts the resulting checkpoint history. Checkpoint validation now permits a skipped commit marker only when the corresponding uncommitted checkpoint file is present, and continues from a later generation without overwriting the failed file. Remaining coverage includes access-denied mapping at the Win32 boundary and SCM behavior on supported Windows versions. Existing separate tests cover typed journal format and duplicate recovery order.

## Windows validation gate

On disposable Win7 SP1 x86/x64 VMs, use a purpose-created test service, never a built-in or user service. Verify `ChangeServiceConfigW`, query rights, all startup-type values supported by the target OS, access-denied behavior, service deletion during recovery, and process interruption at every durable/mutation boundary. Do not claim VM coverage until actual outputs and images are recorded. Keep any application UI/CLI entrypoint disabled until these gates and the journal-root ACL, discovery and power-loss contracts are closed.

The typed service record and recovery path are persisted through `LockedJournalStorage`, and the guarded Win32 backend compiles for both configured Win7 targets. It has not been exercised against SCM writes or on Win7. Root ACL security, atomic transaction discovery, target races with external actors, and power-loss behavior remain unresolved; no UI/CLI service operation may be enabled until the mock matrix and shared persistence release gates are verified.
