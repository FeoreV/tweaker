# Backup and mutation contract (design)

This contract remains a design, not a release guarantee. `RegistryJournal` now connects the typed registry record to an injectable `JournalStorage`; the Windows `FileJournalStorage` implementation writes exclusive files with `FILE_FLAG_WRITE_THROUGH`, calls `sync_all`, bounds rereads and relies on `RegistryJournal` to decode and compare exact bytes before reporting success. Callers must obtain `LockedJournalStorage`, which owns an OS-level exclusive lock handle and is required by the `JournalStorage` implementation. A child-process test verifies that another process cannot acquire the same transaction lock while it is held. `FileJournalStorage::create_private` creates a new non-reparse root, while `open` rejects existing roots that fail policy; both require fixed NTFS with persistent ACL support. Tests currently exercise it on the host NTFS volume.

`FileJournalStorage::scan` validates per-transaction sequence, commit markers, record identities, and record CRCs; a valid committed prefix can be reopened with `RegistryJournal::resume`. Commit-marker files are first written and flushed under a `.commit.pending` suffix, read back, then published to the committed `.commit` name with `MoveFileExW(MOVEFILE_WRITE_THROUGH)`. An incomplete journal tail or a pending marker blocks resume. Checkpoint markers follow the same publication protocol. A test-only injector faults create/write/flush/readback/publish boundaries; tests reopen the NTFS-backed files to verify which artifacts are committed. The process-termination probe covers 31 cuts across record writes, initial checkpoint publication and recovery snapshot-ID rotation; reopening checks raw artifacts and published state. These tests establish process-termination behavior on the host, not sudden power-loss or device-cache durability. CRC detects accidental corruption, not malicious edits. `discover_transactions` now holds a root-wide discovery lock, and `lock_transaction`/`create_new_transaction` use that lock while opening or creating transaction lock files. Transaction-ID enumeration is atomic relative to this implementation’s lock-file creation; direct external filesystem writers remain outside the guarantee. `FileJournalStorage::lock_registry_mutations` provides a conservative root-wide exclusive barrier, covering registry name case variants, view aliases and HKCR merged-path overlap. `FileRecoverySession` retains this guard for its lifetime. `FileTransactionSession` owns a fresh transaction journal and acquires the barrier around each generic query -> backup persistence -> apply operation; its tests verify backup visibility before apply and that barrier contention prevents the query and journal write. The guarded Win32 registry backend is routed through this session; direct use of generic `apply_one` still does not enforce locking. The transaction lock must be acquired before the registry barrier. `LockedJournalStorage::open_recovery_checkpoint` rescans and binds append-only checkpoint generations to the exact committed prefix while retaining the transaction lock. Checkpoint v4 binds typed records and the separate recovery snapshot-journal ID; the reader continues to accept v3 registry-only checkpoints. `FileRecoverySession::start` generates and atomically reserves a snapshot ID; `start_with_id` accepts one explicitly. Both persist identity before recovery starts. On restart, `resume` loads the ID and resumes that journal while holding the registry barrier and both journal locks. If its journal has an incomplete tail, resume commits a new ID at unchanged progress before retrying; the old journal and tail are preserved. Checkpoint loading rejects ID changes when progress also changes. `recover_journal_prefix` converts records, recovers in reverse, persists each pre-restore state through the recovery journal, and commits progress after each step. Host-NTFS integration tests use a mock backend and cover closing/reopening both journals after an interrupted restore and rotating after an injected incomplete tail. This testing does not establish atomic rename metadata durability across sudden power loss. The journal root now has protected ACL and ancestor checks, but namespace replacement by the trusted profile owner remains possible; external path writers and power-loss guarantees remain unresolved. The backend accepts only fixed NTFS volumes that report persistent ACL support. Guarded Win32 registry and typed service prototypes exist but no UI/CLI mutation entrypoint is wired. Callers must not use this path to authorize system mutations until these gaps are closed and crash recovery is tested. Microsoft documents write-through behavior for [`CreateFile`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) and explicit flushing with [`FlushFileBuffers`](https://learn.microsoft.com/en-us/windows/win32/fileio/flushing-system-buffered-i-o-data-to-disk); these API contracts do not replace tests on the actual filesystem and storage stack.

## Identity and pre-state

Each transaction has a unique ID and an ordered list of operations. Every operation identifies the target precisely, including registry hive, full path, value name, and registry view. Preserve value absence separately from a present zero-length value; preserve the native registry type and exact bytes. Capture key existence and enough parent-key state to remove only keys created by the transaction without deleting unrelated data. Service snapshots include every configuration field and runtime state changed by the operation. Filesystem snapshots must capture existence, object type, complete content and metadata needed for exact restoration; symlinks, permissions, streams and concurrent changes require explicit support. Unsupported snapshots fail closed.

## Ordering and crash recovery

1. Serialize access to each target and query its current state. Identify access errors separately from absence.
2. Write a versioned, uniquely named journal record containing target, before-state, intended change and transaction/sequence IDs. Flush the record and ensure the persistence guarantees required on the actual filesystem; reopen and validate it before the mutation. If any step fails, do not mutate.
3. Apply one operation and record its outcome. On a crash after persistence but before outcome recording, the operation is *possibly applied*: recovery must inspect the target and treat the saved before-state as authoritative only after handling concurrent modifications explicitly. Never silently overwrite an unrelated later change.
4. On failure, report partial application and offer recovery using persisted records in reverse order. Log individual restoration failures and preserve the journal for retry. An absent prior value is restored by deletion, not a guessed default. Never mark a transaction restored until restoration has been verified.
5. Handle duplicate targets deterministically: record each before-state in operation order and undo in reverse. Define transaction locking, recovery ownership and conflict detection before real backends are enabled.

The durable-storage implementation must explicitly document Windows filesystem flush, atomicity and corruption behavior. A failed or truncated journal must never be silently treated as a successful backup. Restore points are optional supplemental protection, never a replacement for snapshots.

## Boundaries

Registry and service access are abstracted behind query/apply/restore interfaces for mock tests. The transaction coordinator alone authorizes a mutation after the backup store reports durable, validated persistence. The actual backing store must be injectable to exercise write, flush, validation and recovery failures. No mock result proves OS-level durability or correct Win32 behavior.

Operations such as package installers, shell commands, power plans, cleanup and repair can affect resources beyond an observable snapshot. They are unsupported until their complete effects can be captured and restored under the project's mandatory invariant. Do not silently mark them reversible.

## Required tests

Use in-memory backends and fault injection: missing versus empty values; exact type/bytes; failed query/write/flush/re-read prevents mutation; multiple operations and duplicate targets; mutation failure and partial failure; interruption after persistence and after mutation; reverse restoration; external-change conflict; restoration failure and retry; malformed or unsupported journal versions. Add Windows VM tests for registry views, service lifecycle, filesystem persistence and crash recovery before release. Never run destructive tests against the user's machine.

## Current Win32 registry backend scope

`WindowsRegistryBackend` is guarded by a `RegistryMutationLock` and is constructed by `FileTransactionSession::apply_registry` or `FileRecoverySession::run_registry`. The transaction session persists the queried before-state before applying. The backend opens existing keys only, preserves exact native type and bytes, removes a value to restore prior absence, and verifies writes by querying again. It does not create or delete keys; writing into a missing key and restoring `KeyMissing` fail closed. The 32-bit build directs writes to the 64-bit registry view per project policy. No application UI/CLI entrypoint currently enables these calls. The generic coordinators remain for mock testing; do not pass a real Windows backend through an unguarded generic path. This prototype does not close root ACL and external namespace-tampering, registry external-change conflict handling, power-loss, service/filesystem, or Win7 VM requirements. Cooperative transaction-ID discovery is serialized by a separate root lock. No live registry mutation has been exercised.

Both journal and checkpoint marker publication now use `MoveFileExW` with `MOVEFILE_WRITE_THROUGH` after closing, flushing, and reading back the pending marker. Microsoft's [MoveFileExW contract](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw) specifies write-through behavior; this is a stronger publication request than a plain rename, but the host tests do not simulate sudden power loss or prove durability through a filesystem/device cache stack.

The typed service startup-type write and recovery prototype now exist behind managed file transaction/recovery sessions, but they are not approved for application use and have not been exercised against the real SCM. The only supported prototype operation is changing the start type of an existing local service; do not add other service effects without a reviewed snapshot/recovery contract. It uses a typed durable service record, not a registry value. See [`service-mutation-contract.md`](service-mutation-contract.md) for ordering, conflict handling, mock coverage and the outstanding VM gate.
